# セキュリティチェック（個人用AIライティングアプリ）

## この前提を必ず踏まえる

このアプリは **単一ユーザーがローカルで動かすツール**。DBなし、ログイン機構なし、外部公開を想定していない設計（`CLAUDE.md` にも明記されている）。

そのため、一般的なWebアプリのセキュリティレビューでよく出てくる「認証がない」「CSRF対策がない」「セッション管理が甘い」「マルチテナント分離がない」といった指摘は、この設計を無視した的外れな指摘になる。**これらは指摘しないこと。**

本当にチェックすべきなのは「ローカル1ユーザー前提が崩れる経路」——具体的には、APIキーが意図せず外に漏れる、Gemini（外部モデル）の出力を信頼しすぎてブラウザ上で実行してしまう、エラー情報が機微データを晒す、といった筋。この前提を頭に入れてから以下を進める。

## 対象範囲

デフォルトでは `app.py`, `utils/*.py`, `pages/*.py`, `requirements.txt`, `.streamlit/`, `.gitignore` をひと通り見る。ユーザーが特定のファイルや「直近の変更だけ」を指定した場合はその範囲に絞ってよい。

実際にファイルを読み、`Grep` でパターンを探すこと。読まずに一般論で「大丈夫そうです」と結論づけない——それはこのスキルの価値をゼロにする。

## チェック項目

### 1. APIキー・シークレットの漏洩

なぜ重要か：このアプリの唯一の「秘密」は Gemini APIキー。個人利用とはいえ、リポジトリ共有やスクショ、ログ共有で漏れると実害（課金・不正利用）に直結する。

- `.py` ファイル内にAPIキーらしき文字列（`AIza...`、`sk-...`、`api_key\s*=\s*["']` など）がハードコードされていないか `Grep` で探す。
- `.gitignore` に `.streamlit/secrets.toml` と `.env` が含まれているか確認する（外れていたら重大）。リポジトリがまだ `git init` されていない場合は、設定ファイル自体の正しさは確認できるが「実際にコミット済みかどうか」までは検証できないので、その旨を一言添えて区別する（例: 「設定は正しいが、gitリポジトリ化されていないため実際の追跡状態は未検証」）。
- `.streamlit/secrets.toml.example` にプレースホルダ以外の実キーが紛れ込んでいないか。
- `utils/gemini_client.py` の `get_api_key()` の優先順位ロジック（`session_state` → `st.secrets` → 環境変数）が変わっていないか、また取得したキーが `st.write` / `st.markdown` / `print` / 例外メッセージなどでUIやログに出力される経路がないか。
- ログや一時ファイル（例: `streamlit_log.txt`）がリポジトリ内に**存在すれば、新旧を問わず毎回**中身を確認する。「新しく生成されたものだけ見る」と思い込まないこと——`streamlit_log.txt` は現在 `.gitignore` に含まれておらず、常にチェック対象。実際に中身を読み、APIキーだけでなく、IPアドレスやローカルパスなど「個人・環境に紐づく情報」が含まれていないかも見る。含まれていて `.gitignore` 対象にもなっていなければ注意として報告する。

### 2. Streamlit特有の脆弱性

なぜ重要か：`unsafe_allow_html=True` を使うと、そこに渡した文字列がそのままブラウザでHTML/JSとして実行される。ローカル1ユーザー用途でも、Gemini出力（外部モデルの生成物であり完全には信頼できない）をそのまま流し込むと、意図しないスクリプト実行につながりうる。

- `Grep` で `unsafe_allow_html` を探す。見つかったら、そこに渡っている文字列が Gemini の生成結果やユーザー入力を含むか確認する。含む場合は指摘する（重大寄り）。静的な自前HTMLだけであれば「該当箇所はあるが問題なし」と明記する。見つからなければ「未使用」と明記する。
- `st.file_uploader` などファイルを受け取る処理があるか確認する。あれば保存先パスの組み立て方（パストラバーサルの余地がないか）、拡張子・サイズ制限の有無を見る。現状のページ構成に存在しなければ「該当なし」と明記すればよい。
- `st.session_state` にAPIキー以外の機微な情報（個人情報を含む生成テキストなど）を長期保持していないか、想定外のキー衝突がないか軽く確認する。

### 3. Gemini API呼び出し周りの安全性

なぜ重要か：各ページは `system_instruction`（ツールの人格・ルール）と `prompt`（ユーザー入力を含む実際の依頼）を組み立てて呼び出す設計になっている。この分離が崩れると、ユーザー入力が意図せず「指示」側に混入したり、エラー処理がAPIキーや内部情報を画面に漏らしたりしうる。

- 各 `pages/*.py` で `system_instruction` の組み立てを見て、ユーザー入力（`st.text_input` などの値）がそのまま `system_instruction` 文字列の中に混入していないか確認する。既存ページは `prompt` 側にのみユーザー入力を入れる作りになっているはずなので、それが崩れているページがあれば指摘する。
- `generate_stream` / `generate` の呼び出し周りに try/except があるか確認する。**try/exceptが存在しないこと自体は問題ではない**——Streamlitのデフォルトのエラー画面が出るだけで、個人用ローカルツールとしては許容範囲。指摘すべきなのは、明示的に例外を捕まえた上で、その内容（APIキーや内部パスを含む文字列）を `st.error` / `st.write` 等でそのまま画面に出しているケースだけ。見つからなければ「該当なし」でよい。
- Gemini の出力をそのままファイル書き込み・シェルコマンド・`eval`/`exec` に渡すようなコードが追加されていないか確認する。現状は `st.write_stream` で画面表示するだけなので該当しないはずだが、新しいページでこのパターンが増えていないか毎回見ておく。

### （任意）依存パッケージの既知脆弱性

これはユーザーが選んだ中心3項目には含まれていないので、毎回自動ではやらない。ただしユーザーが「依存関係もついでに」と言った場合は、`pip install pip-audit && pip-audit -r requirements.txt` の実行を提案する。

## レポート形式

チャット内に直接、Markdownで以下の形式で出力する（ファイルには保存しない）：

```
# セキュリティチェック結果（YYYY-MM-DD）

## 🔴 重大
（あれば `file:line` + 何が問題か + 直し方。なければ「なし」）

## 🟡 注意
（同上）

## 🔵 確認したが問題なし
各チェック項目について、実際に確認した上で問題がなかったものをここに列挙する。
空にしない・省略しない——ここがあることで「ちゃんと全項目見た」ことが伝わる。
```

## 判断の指針

- 実際にコードを読んで確認できたことだけを報告する。存在しない問題をでっち上げない。
- 深刻度は「このアプリの実際の利用シーン（個人がローカルでGeminiに文章を投げるツール）で本当に起こりうるか」で判断する。一般的なチェックリストを機械的に当てはめない。目安: 🔴＝APIキーそのものが漏れる／外部から不正利用される経路（例: キーのハードコード、UIへのキー表示）。🟡＝直接の実害はないが個人・環境に紐づく情報が漏れる、または将来の変更で🔴に発展しうる経路（例: IPアドレスが残ったログがgit管理対象になりうる、例外メッセージの画面表示）。この2つを同列に並べず、レポート内でも実害の大きさが伝わる書き方をする。
- 「〜すべき」を並べるだけでなく、なぜそれが今回の設計上リスクなのか一言添える。理由が分かれば、ユーザー自身も次にコードを書くときに気をつけられる。
